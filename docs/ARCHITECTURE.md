# Архитектура лаборатории

Этот документ объясняет, какие части приложения являются точной визуальной моделью, а какие читают реальную память.

## Почему нужны и модель, и unsafe

`unsafe` позволяет увидеть настоящий снимок runtime, но не позволяет поставить выполнение посередине одной операции `m[key] = value`. Например, современный rehash таблицы завершается до возврата управления пользовательскому коду. Мы можем сравнить память только **до** и **после** записи.

Детерминированная модель решает другую задачу: раскладывает одну операцию на микрошаги и объясняет каждый переход. Поэтому вкладки дополняют друг друга:

```text
безопасная модель  →  объясняет причинно-следственную связь
unsafe-инспектор  →  подтверждает итог на реальном runtime
```

## Современная Swiss Table

Модель в `internal/lab/swiss.go` повторяет следующие свойства Go 1.25:

- 8 слотов в одной группе;
- один control byte на слот;
- `0x80` — empty, `0xfe` — deleted, `0hhhhhhh` — занятый H2;
- `H1 = hash >> 7`;
- `H2 = hash & 0x7f`;
- triangular/quadratic probe sequence по группам;
- максимальная средняя загрузка `7/8`;
- small map из одной группы;
- удвоение таблицы;
- split максимальной таблицы;
- extendible hashing через `globalDepth` и directory;
- возможность нескольких directory entries указывать на одну table;
- tombstone при удалении из полной группы.

В Go 1.25 реальный `maxTableCapacity` равен 1024. В интерфейсе по умолчанию стоит учебный предел 32, иначе для первой демонстрации split пришлось бы вставить около 900 элементов. Предел 1024 можно выбрать вручную.

### Нюанс `pruneTombstones`

Go 1.25 перед grow пытается консервативно удалить ненужные tombstones, если они занимают хотя бы 10% таблицы. Точное решение зависит от probe sequences всех живых ключей.

Учебная модель при достаточном числе tombstones делает безопасный rehash той же ёмкости. Это сохраняет семантику поиска и наглядно показывает восстановление `growthLeft`, но в trace честно отмечено, что реальный алгоритм prune более избирателен.

## Классическая bucket map

Модель в `internal/lab/legacy.go` показывает:

- `2^B` основных бакетов;
- 8 слотов в `bmap`;
- tophash-фильтр;
- overflow-цепочку;
- порог обычного роста около 6.5 элементов на бакет;
- одновременное существование `buckets` и `oldbuckets`;
- X/Y-разделение по новому биту;
- `nevacuate`;
- `growWork` только в записях и удалениях;
- чтение из old или new массива в зависимости от маркера evacuated.

Same-size grow из-за избытка overflow описан в конспекте, но основной интерактивный сценарий использует обычное удвоение: именно оно лучше всего показывает X/Y-разделение.

## Unsafe build tags

Инспекторы не могут использовать один layout для всех версий:

```go
//go:build goexperiment.swissmap
```

компилирует зеркало `internal/runtime/maps.Map`, а:

```go
//go:build !goexperiment.swissmap
```

компилирует зеркало legacy `runtime.hmap`.

Обе реализации работают только с принадлежащей лаборатории `map[int]int`. Благодаря фиксированным типам ключа и значения известен layout группы/бакета. Универсальный инспектор произвольных типов потребовал бы также зеркал внутренних type descriptors и был бы намного опаснее.

## Потокобезопасность

HTTP-сервер защищает состояние лаборатории одним `sync.Mutex`. Это важно по двум причинам:

1. встроенная `map` не допускает конкурентные запись/запись и чтение/запись;
2. снимок интерфейса должен соответствовать ровно одной завершённой операции.

Сервер слушает `127.0.0.1`, а не все сетевые интерфейсы, и не принимает произвольный код или файловые пути.

## Граница точности

Гарантируется:

- правильная причинная модель поиска, роста и маршрутизации;
- повторяемость сценариев;
- соответствие unsafe-layout выбранной сборке toolchain;
- отсутствие внешних зависимостей.

Не гарантируется:

- стабильность unsafe-layout на будущих версиях Go;
- совпадение учебного hash с внутренним hasher;
- совпадение точного физического распределения модели с реальной map;
- использование лабораторного кода как библиотеки в production.
