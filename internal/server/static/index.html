    ПРАВИЛЬНАЯ МЕНТАЛЬНАЯ МОДЕЛЬ

    Две разные эпохи Go map

    Синтаксис языка не изменился, но под капотом map в актуальном Go устроена уже не так, как в старых статьях про hmap и nevacuate.

    Главное исправление исходного разбора

    Формула 2^(B−1) не была гарантией

    В старой реализации growWork пытался эвакуировать целевой бакет операции и бакет nevacuate. Они могли совпасть, а целевой бакет мог быть уже перенесён. Поэтому одна запись гарантировала прогресс минимум на один ещё не готовый бакет, но не гарантировала два новых.

    Для N старых бакетов ⌈N / 2⌉ ≤ изменяющих операций ≤ N точное число зависит от хешей записываемых ключей; чтения дают 0

    СРАВНЕНИЕ

    Что именно растёт

    Go 1.24+

    Swiss Table

    1. Hash делится на H1 и семибитный H2.
    2. Group хранит 8 пар и 8 control bytes.
    3. Table использует quadratic probing.
    4. Directory верхними битами выбирает таблицу.
    5. Grow целой выбранной таблицы синхронен; при 1024 слотах таблица делится.
    до Go 1.24 / noswissmap

    Bucket map

    1. Младшие B бит выбирают один bmap.
    2. tophash фильтрует 8 слотов бакета.
    3. overflow продолжает переполненный бакет.
    4. oldbuckets сосуществует с новым массивом.
    5. growWork размазывает эвакуацию по записям и удалениям.

    Как Swiss Table ищет ключ?

    H1 выбирает первую группу. Одной битовой операцией control word сравнивает H2 сразу у восьми слотов. Только совпавшие кандидаты проходят полное сравнение ключа. Empty останавливает поиск; deleted разрешает продолжить.

    Почему удаление оставляет tombstone?

    Если группа была полной, простой empty мог бы преждевременно оборвать поиск ключа, который из-за коллизий лежит дальше. Маркер deleted говорит: «здесь пары уже нет, но probe sequence продолжается».

    Где здесь «инкрементальный» рост?

    В современной реализации одна таблица перестраивается целиком. Но большая map разделена директорией на таблицы максимум по 1024 слота, и в конкретной записи растёт только одна из них. Работа ограничена небольшой частью всей map.

    Что делает make(map[K]V, hint)?

    Hint помогает runtime заранее подобрать ёмкость и число таблиц. Это уменьшает число последующих перестроений, но hint не является жёсткой capacity и не меняет семантику map.

    Почему map не потокобезопасна?

    Параллельные запись/запись и чтение/запись без синхронизации — гонка данных. Для владения map используют mutex, передачу владения через канал или специализированный sync.Map в подходящих сценариях.

    Можно ли использовать unsafe-инспектор в продукте?

    Нет. Layout runtime не является публичным контрактом и меняется между версиями. Лаборатория компилирует разные инспекторы по build tags и всё равно должна считаться версионно-зависимым учебным кодом.
